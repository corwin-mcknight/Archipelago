# Contributing to Archipelago

**GitHub is the source of truth for planning and coordination.** Use [issues](https://github.com/corwin-mcknight/Archipelago/issues) for bugs, proposals, acceptance criteria, and implementation progress; [milestones](https://github.com/corwin-mcknight/Archipelago/milestones) for roadmap outcomes; and the [project](https://github.com/users/corwin-mcknight/projects/1) for the work queue. Keep design contracts and explanations of the current system in [docs/Design](docs/Design) and [docs/Kernel](docs/Kernel), updating them with the code. Record implementation plans and follow-up work in linked issues so the repository does not accumulate a second backlog.

**Start with one reviewable issue.** Search for existing work, describe the problem and intended behavior, and define observable acceptance criteria and the checks needed to establish them. Link relevant design documents, code, dependencies, and a milestone. Larger outcomes belong in parent issues with focused sub-issues. Record blockers as issue dependencies when available. Distinguish reproduced failures from source review findings: preserve the suspected failure path and uncertainty until a test or observation confirms it.

**Keep the queue meaningful.** Backlog holds work that is not yet selected; Ready means the scope, acceptance criteria, and prerequisites are clear; In progress means implementation has started; In review means there is a reviewable PR; Done means the acceptance criteria have been demonstrated. An issue with unresolved blockers stays in Backlog. Update the issue when scope or decisions change, and link the evidence before closing it or completing its milestone.

**Use an issue, a branch, and a PR for each change.** Work on a focused branch, preserve unrelated changes, and open a draft PR early if useful. Reference the issue in the PR; use `Closes #123` only when the change completes its acceptance criteria, or `Refs #123` for partial work. The description should explain the concrete problem, resulting behavior, validation, and remaining limitations. Put additional work in linked issues rather than expanding a PR beyond a reviewable scope.

**Validate the behavior you changed.** Follow [BUILDING.md](BUILDING.md) for setup and commands and [Development](docs/Development.md) for code conventions. Apply CamelCase type and UPPER_SNAKE constant conventions to outliers as their code is touched; avoid a whole-tree rename that displaces substantive work. Use focused regression tests when behavior changes, then run the relevant existing checks. Report commands, target architecture or host, outcomes, and checks not run. Keep hosted tests, coverage, QEMU on each architecture, ThreadSanitizer, bounded fuzzing, image builds, and physical-board results distinct. A JH7110 image build verifies compilation and packaging; physical-board claims need board execution evidence. [Testing](docs/Kernel/Testing.md) explains the test system, and [Actions](https://github.com/corwin-mcknight/Archipelago/actions) retains run results and artifacts.

**Merge through a passing PR.** Required CI must pass and review conversations must be resolved before merging into `main`. A second person's approval is not required for solo work; review the final diff and results yourself when no other reviewer is available. Squash focused changes to keep the history readable. After merging, close completed issues, move their project items to Done, and leave any unfinished acceptance criteria in explicitly linked follow-up work.
